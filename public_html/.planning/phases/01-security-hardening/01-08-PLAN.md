<objective>
Replace all `->where("... LIKE '%.$var.'%' ...", NULL, FALSE)` patterns with `$this->db->like()` / `or_like()` in the first 13 files of the 26-file SEC-05 bulk fix (SEC-05 batch A).

Purpose: The `NULL, FALSE` third argument to `where()` disables CI3's escaping, making every DataTables search input a SQL injection vector. CI3's `like()` / `or_like()` methods call `escape_like_str()` internally and produce semantically identical queries without the injection risk.

Output: 13 model/controller files with all LIKE string-interpolation patterns replaced by parameterized CI3 Query Builder calls.

<!-- The canonical replacement pattern — verified from CI3 DB_query_builder.php and Appointment_model.php -->

BEFORE (all occurrences follow this exact structural pattern):
```php
->where("(col1 LIKE '%" . $search . "%' OR col2 LIKE '%" . $search . "%' OR col3 LIKE '%" . $search . "%')", NULL, FALSE)
```

AFTER (semantically equivalent, properly escaped):
```php
->group_start()
->like('col1', $search)
->or_like('col2', $search)
->or_like('col3', $search)
->group_end()
```

Single-column variant:
```php
// BEFORE:
->where("col LIKE '%" . $search . "%'", NULL, FALSE)
// AFTER:
->like('col', $search)
```

CRITICAL: Never use the array form `$this->db->like(['col1' => $v, 'col2' => $v])` — this produces AND, not OR, changing query semantics silently.

Confirmed example from Appointment_model.php (lines 45-46 and 72-73):
```php
// BEFORE:
->where("(id LIKE '%" . $search . "%' OR patientname LIKE '%" . $search . "%' OR doctorname LIKE '%" . $search . "%')", NULL, FALSE)

// AFTER:
->group_start()
->like('id', $search)
->or_like('patientname', $search)
->or_like('doctorname', $search)
->group_end()
```
